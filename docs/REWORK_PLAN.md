## 1. 현재 진단 (무엇이 틀려 있었나)

### 1.1 손익 측정이 틀렸다
`tools/calculate_total_pnl.py`가 `fapiPrivateGetIncome`을 **기간 인자 없이** 호출한다.
바이낸스는 이 경우 최근 7일만 돌려준다. 따라서 출력되는 "누적 손익", "Calculated Starting
Balance", "Total Net Yield (ROI) since start"는 전부 7일 롤링 값이다.
주간 리포트(`~/agent/scripts/btc-weekly-stats.sh`)가 이 값을 그대로 쓰고 있어
`btc-weekly-stats.log`의 +7.45% / +7.66% / +8.68%는 모두 잘못된 수치다.

**실제 값** (1일 단위로 전 구간 페이징해 재집계):

| 항목 | 값 |
|---|---|
| 테스트넷 충전 이력 | 4/29, 5/11, 5/22, 6/4 각 +5,000 USDT (합계 19,989.33) |
| 계좌 정합 구간 | 2026-06-04 마지막 충전 이후만 (5,000 + 343.66 = 5,343.66 ✓) |
| 6/4 이후 순손익 | 실현 +427.93 / 수수료 -57.87 / 펀딩 -26.39 → **+343.66 USDT (+6.87%)** |
| 미실현 포함 | 5,361.51 USDT (**+7.23%**) |

6/4 이전 잔고는 테스트넷 쪽에서 초기화된 것으로 보여 전 기간 ROI는 이 원장으로 계산 불가.

### 1.2 수익이 알파가 아니라 사고에서 나왔다
6/4 이후 청산 6건: 7/26 -8.26 / 7/27 -39.01 / 7/28 +33.91 / **9/14 +371.73** / 9/14 -15.05 / 9/15 +58.81.
승 3 패 3인데 수익의 거의 전부가 9/14 한 건이다. 그 포지션은 7/28 16:23에 63,875.8에 진입한
롱인데, **봇이 7/29~9/14 47일간 죽어 있는 동안 방치**되다가 77,643.5에 청산됐다.
전략이 잡아낸 수익이 아니라 다운타임이 만든 우연이다.

### 1.3 주문 경로 버그로 한 달간 진입 불가
`live_trader.py` `open_position()`:

```python
ticker = self.exchange.fetch_ticker(self.symbol)
bid_price = ticker.get('bid') or ticker.get('last') or ticker.get('close')
ask_price = ticker.get('ask') or ticker.get('last') or ticker.get('close')
limit_price = float(bid_price if direction == 'BUY' else ask_price)   # ← 전부 None이면 TypeError
```

`or` 체인은 현재 커밋되지 않은 수정본이고, 그 이전 버전(`float(ticker['bid'])`)일 때
`regime_bot.log.4`/`.3`에 `TypeError: float() argument must be ... not 'NoneType'`이 **65,900회**
찍혔다. 6/24~7/27 약 한 달간 신규 진입이 사실상 막혀 있었다.
지금 버전도 네 값이 모두 None이면 똑같이 터진다. **가드가 아직 불완전하다.**

### 1.4 거래 기록에 구멍
`trading_data.db`의 `trade_logs`에 7/28 16:23:25 LONG 0.027 진입(OPEN)이 없다.
id 7 → id 8로 건너뛴다. 가장 큰 수익을 낸 포지션의 진입 기록이 DB에 없다는 뜻이다.

### 1.5 백테스트와 실제가 따로 논다
봇이 돌던 6/24~7/29 구간을 백테스트하면 **20건 거래 / -1.33%**인데,
실제 체결은 3라운드트립뿐이었다. 위 1.3이 주원인.

## 4. 바이낸스 환경에 맞춘 백테스트 재설계 ← 이번 작업의 핵심

현재 `research/backtester.py`가 실제 바이낸스 USDⓈ-M 선물과 다른 지점들. 위에서부터 영향이 크다.

| # | 현재 | 실제 | 대응 |
|---|---|---|---|
| a | 펀딩비 없음 | 8시간마다 명목가 기준 정산 | `fapiPublicGetFundingRate` 이력을 받아 보유 구간에 실제 요율 적용. 숏이 많아 부호가 유리할 수 있으므로 반드시 실측값으로 |
| b | 전 체결 taker 0.04%. `maker_fee`는 선언만 되고 **한 번도 안 쓰인다** | 진입은 지정가(maker 0.02%), 청산은 시장가(taker 0.04%), 지정가 미체결 시 시장가 폴백 | 주문 타입별 수수료 분리. 라이브의 "지정가 추격" 로직을 백테스트에도 근사 반영 |
| c | 슬리피지 고정 0.02% | 호가 스프레드 + 변동성에 비례 | 최소한 ATR 비례 모델. 4h 봉이라 봉내 체결가 가정이 성과를 좌우함 |
| d | 청산가 근사 (`유지증거금 = 명목가 × 0.05/leverage`) | 바이낸스 MMR 계층(브래킷)별 | 실제 브래킷 테이블 적용. 현재 레버리지 1~2배라 영향은 작지만 레버리지를 올릴 거면 필수 |
| e | 수량/가격 정밀도 없음 | 틱사이즈, 스텝사이즈, 최소명목가 5 USDT | `load_markets()`의 `precision`/`limits`로 반올림. 소액 계좌에서 특히 중요 |
| f | 진입 캔들에서는 SL/TP 미검사 | 진입 직후에도 발동 가능 | 진입 봉부터 검사. (지금은 낙관적) |
| g | 봉 내 SL·TP 동시 도달 시 SL 우선 | 알 수 없음 | 현행 유지(보수적). 단 1h/15m 서브캔들로 실제 순서 확인 가능하면 그쪽이 정확 |
| h | 부분체결·미체결 없음 | 지정가는 안 채워질 수 있음 | 미체결률 가정을 파라미터화해 민감도 확인 |
| i | 교차/격리 마진 구분 없음 | 증거금 모드에 따라 청산가가 다름 | 라이브 설정과 일치시킬 것 |

추가로 백테스트와 라이브의 **국면 판정 경로가 다르다**:
라이브(`run_regime_bot.py`)는 매번 최근 200봉만 받아 그 안에서 국면 확정 루프를 처음부터 돌린다.
국면 확정은 경로 의존적이라, 전체 이력으로 돌리는 백테스트와 결과가 달라질 수 있다.
**두 경로를 같은 함수로 통일**하는 것이 이번 재설계의 필수 항목이다.

검증 방법: 재설계한 엔진으로 봇이 실제 돌던 구간(6/24~7/29, 9/14~)을 돌려
체결 수와 손익이 실제 기록과 얼마나 맞는지 **추적오차를 수치로 남긴다.**
이 오차가 작아지기 전까지 최적화 결과는 믿지 않는다.

## 5. 전략 재탐색 절차 (hwdesktop 위임)

### 5.1 원칙
- **워크포워드 분석(WFA)**: 인샘플 6개월 → 아웃샘플 2개월 롤링. 아웃샘플 성과만 집계한다.
  지금처럼 전 구간 최적화 후 전 구간 성과를 보는 방식은 쓰지 않는다.
- **파라미터 고원 탐색**: 최적점 하나가 아니라 이웃 파라미터에서도 성과가 유지되는 영역을 고른다.
  단일 최고점은 거의 항상 과최적화다.
- **비용 스트레스**: 수수료·슬리피지를 2배로 놓고도 살아남는 설정만 후보로 남긴다.
  현 전략은 슬리피지 0.2%에서 마이너스로 뒤집힌다.
- **회전율 패널티**: 연 101회전은 비용 리스크가 크다. 회전율이 낮으면서 비슷한 성과를 내는
  설정을 선호한다.
- 평가 지표는 총수익률이 아니라 **아웃샘플 샤프 · MDD · PF · 구간별 일관성**.

### 5.2 데스크탑 환경
확인 완료 (2026-09-17): `HyunwooDesktop`, WSL2, Python 3.12.3, 12코어, RAM 19GB,
RTX 2060 6GB, `~/workspace` 존재. `eht_mk2`는 아직 없음(`crypto-trading`이라는 옛 사본만 있음).

준비 절차:

```bash
# 미니PC(dohoon)에서
scripts/on-desktop.sh 'cd ~/workspace && git clone https://github.com/hwchoi0302/eht_mk2.git'
scripts/on-desktop.sh 'cd ~/workspace/eht_mk2 && python3 -m venv venv && \
  ./venv/bin/pip install ccxt pandas numpy python-dotenv optuna'
```

주의:
- 데스크탑에는 **실거래 키를 두지 않는다.** 백테스트는 공개 OHLCV만 필요하므로 `.env` 불필요.
- OHLCV는 데스크탑에서 직접 받게 한다(`research/download_historical.py`). 14MB짜리
  `trading_data.db`를 ssh로 나르지 말 것.
- optuna는 12코어 `n_jobs` 병렬. GPU는 이 워크로드에 쓸 일이 없다(트리 기반 탐색).
- `on-desktop.sh` 종료 코드 **69** = 기동 실패. 재시도하지 말고 작업 보류 후 결과에 명시.

실행 예:

```bash
scripts/on-desktop.sh 'cd ~/workspace/eht_mk2 && ./venv/bin/python research/run_full_sweep.py ...'
```

### 주문 방식 — 전량 시장가로 전환

지정가 진입 + 4회 가격추격 + 시장가 폴백 경로(`manage_pending_limit_order`,
약 120줄)를 통째로 제거했다. 진입·청산 모두 단일 시장가 주문이다.

부수 효과로, SL/TP를 거래소에 `STOP_MARKET` / `TAKE_PROFIT_MARKET`
(`closePosition=True`, `workingType=MARK_PRICE`)로 올리게 했다. 기존에는 봇이
30초 루프에서 직접 가격을 보고 청산해서, 봇이 죽으면 SL/TP가 아예 작동하지
않았고 살아 있어도 최대 30초 늦었다. 이제 봇 상태와 무관하게 체결되고,
백테스트의 "트리거 가격 체결" 가정과도 일치한다.

## A.4 워크포워드 하네스 (`research/strategy_lab.py`)

5.1의 원칙을 코드로 옮겼다. 인샘플 6개월 → 아웃샘플 2개월, 2개월씩 롤링.
BTC 4h 기준 16개 구간이 나온다. **아웃샘플 성과만 집계한다.**

- 파라미터 선택은 `plateau_pick()` — 인샘플 상위 30% 조합을 모아 각 축의
  중앙값에 가장 가까운 실재 값으로 스냅한다. 단일 최고점을 쓰지 않는다.
- 선택 점수는 총수익률이 아니라 `샤프 − 회전율패널티 − MDD패널티`.
  연 50회전을 넘는 만큼, MDD 25%를 넘는 만큼 깎는다.
- 비용 1배와 2배를 따로 돌려, 비용 가정이 틀려도 살아남는지 본다.

### 하네스 자체에서 잡은 버그 두 건

1. **워밍업이 평가 창을 잡아먹었다.** 전략들은 `signals.iloc[:warmup] = 0`으로
   초기 신호를 죽인다. 4h 봉에서 6개월은 약 1,100봉이라 워밍업 96봉이 묻혔지만,
   1d 봉에서는 6개월이 약 180봉뿐이라 워밍업이 창 전체를 덮어 **거래가 한 건도
   나오지 않았다** (삼중 EMA / 듀얼 모멘텀 / 장기 추세 필터 / 시장국면 동적결합이
   모두 0건). `slice_with_warmup()`으로 평가 구간 앞에 260봉을 따로 붙이고,
   성과는 평가 구간만 다시 계산하도록 고쳤다.

2. **손절 그리드가 너무 좁아 추세 전략에 불리했다.** 모든 전략에 3~5% 손절 /
   4~8% 익절만 후보로 줬다. 추세추종 계열은 추세를 타기도 전에 손절로 털린다.
   그리드를 3~8% / 5~20%로 넓히고, 성격이 다른 전략은 개별 그리드를 갖도록 했다
   (`STRATEGY_RISK_GRIDS`). 장기 추세 필터는 이 수정 하나로 아웃샘플
   **-13.5% → +40.4%**, 연 회전율 **103회 → 14회**가 됐다.

두 번째 건은 방법론의 함정을 잘 보여준다. "전략이 나쁘다"는 결론이 사실은
"그 전략에 맞지 않는 탐색 공간을 줬다"였다.

## A.7 파라미터를 더 많이 탐색했더니 더 나빠졌다

A.5의 권고 설정은 워크포워드에서 **손절/익절/레버리지/배분만** 탐색한 결과다.
하위 전략의 기간 파라미터(듀얼 모멘텀 46/94, 삼중 EMA 20/49/96, Z-Score 20/2.0)는
4h 시절 값을 그대로 물려받았다. A.5의 "남은 한계"에 적어둔 대로, 여기를 1d에
맞춰 다시 고르면 더 나아질 여지가 있어 보였다.

그래서 탐색 축을 셋 늘려 다시 돌렸다 (조합 9개 → 162개):

| | 탐색 축 | 조합 | OOS 수익률 | 샤프 | MDD | 일관성 | 비용 2배 |
|---|---|---|---|---|---|---|---|
| 리스크만 (채택) | SL/TP/lev/alloc | 9 | **+76.36%** | **+0.73** | **-17.1%** | **62%** | **+45.13%** |
| 기간까지 확장 | + bull_lookback, bear_mid, side_z | 162 | +56.70% | +0.59 | -21.1% | 56% | +9.02% |

**더 많이 탐색한 쪽이 아웃샘플에서 더 나빴다.** 모든 지표에서 그렇다.
특히 비용 2배에서 +45.13% → +9.02%로 무너진다 — 넓게 탐색해 찾은 설정일수록
비용 가정에 민감하다는 뜻이고, 실계좌에서 가장 위험한 성질이다.

인샘플에서는 당연히 162개 조합 쪽이 더 좋은 점수를 냈다. 탐색 공간이 넓을수록
과거 잡음에 더 잘 맞는 조합을 찾아내기 때문이다. 그리고 그 조합은 다음 구간에서
무너졌다. 이게 워크포워드를 쓰는 이유 그 자체다 — 전 구간 최적화로 봤다면
162개 조합 쪽을 골랐을 것이다.

**결론: 기간 파라미터는 건드리지 않는다.** 권고 설정은 리스크만 탐색한
`config/regime_config_BTC-USDT_futures_1d.json`을 그대로 쓴다.

부수적으로 A.5의 "하위 전략 기간 미최적화"는 더 이상 한계가 아니라 의도적 선택이다.
남은 탐색 여지가 있다면 파라미터를 늘리는 쪽이 아니라 데이터를 늘리는 쪽
(더 긴 이력, 더 많은 종목)에 있다.

# 부록 B — 2026-09-19 전수 탐색

타임프레임 8종(1h/2h/4h/6h/8h/12h/1d/3d) × 국면 3 × 전략 15를 데스크탑

## B.1 탐색 설계

전략 15종을 세 국면에 독립 배치하면 15³ = 3,375가지다. RegimeSwitchingStrategy에서
각 하위 전략은 자기 국면에서만 거래하므로 국면을 분리해 15 × 3 = 45로 줄였다.

- **1단계** 국면 제한 워크포워드로 국면별 순위를 낸다
- **2단계** 1단계 승자를 조합해 재검증 (누수 있음, 대조군)
- **3단계** 중첩 워크포워드 — 폴드마다 그 폴드의 **인샘플만** 보고 국면별
  전략·파라미터를 고른 뒤 그 폴드의 아웃샘플에서 평가

## B.2 도중에 잡은 자체 버그 두 건

### (1) `RegimeSwitchingStrategy`가 `strategy_name`을 읽지 않았다

하위 전략이 DualMomentum / TripleEMA / ZScore 로 하드코딩돼 있었다. 설정에
"BULL=스토캐스틱 RSI"를 써 넣어도 DualMomentum이 돌았다. 반면 라이브
(`switch_strategy_for_regime`)는 `get_strategy_by_name()`으로 이름을 지킨다 —
**라이브와 백테스트가 다른 전략을 돌리는 상태**였다.

이 때문에 첫 2·3단계 결과는 선택된 전략을 전혀 테스트하지 않은 셈이라 폐기했다.
1단계는 `RegimeRestrictedStrategy` 경로로 이름을 지키므로 영향 없었다.

### (2) 하위 클래스가 `super().__init__()`을 호출하지 않는다

`RegimeLiveTrader.__init__`은 부모의 상태 세팅을 복사해 두고 `super()`를 부르지
않는다. 그래서 `LiveTrader.__init__`에 새로 추가한 `_protected_position` 등이
하위 클래스에 없었고, 배포 직후 매 루프 `AttributeError`로 죽었다
(`_ticker_fail_count`도 같은 상태였다). 클래스 속성으로 옮겨 어느 생성 경로든
기본값이 보장되게 했다.

| **A+B+C** | **26.3%** | **1.10** | **-23.6%** | | 19.0% | 0.85 | -27.7% |
| **A+B+C+D** | 21.6% | **1.13** | **-18.7%** | | **16.4%** | **0.90** | **-22.0%** |

**A+B+C는 현행 대비 수익·샤프·낙폭이 모두 개선된다.** 비용 2배에서는 차이가 더
벌어진다 (샤프 0.56 → 0.85, 연환산 11.9% → 19.0%).

분산이 유일한 공짜 점심이라는 통설이 여기서도 그대로 확인됐다. 더 좋은 신호를
찾는 것보다, 상관 낮은 신호를 여러 개 겹치는 쪽이 효과가 컸다.

## C.3 적용하려면 남은 일

현재 봇은 **한 종목·한 주기**만 다룬다 (`config`에 symbol/timeframe이 하나씩).
A+B+C를 돌리려면 구조 변경이 필요하다.

1. 슬리브별로 독립 포지션을 들어야 한다 (BTC 1d, ETH 1d, BTC 4h 동시 보유)
2. 자본을 슬리브에 3분할하고, 슬리브마다 별도 SL/TP 관리
3. 같은 종목에 서로 다른 슬리브가 반대 방향을 낼 수 있다 — 바이낸스 one-way
   모드에서는 상계되므로 hedge 모드로 바꾸거나 넷 포지션으로 합산해야 한다
4. `trade_logs`에 슬리브 식별자 추가

3번이 특히 성가시다. A(BTC 1d)와 C(BTC 4h)가 동시에 BTC를 반대로 잡으면
넷 포지션은 줄어드는데, 백테스트는 둘을 독립으로 계산했다. 이 괴리를
먼저 측정해야 한다 — 넷팅을 반영한 포트폴리오 백테스트가 필요하다.

**즉 현 시점에서 A+B+C는 "백테스트상 유망"까지이고, 배포 가능한 상태가 아니다.**
